# Обґрунтування концептуальної моделі

## 1. Чому був обраний цей домен?

Для проєкту був обраний домен бронювання та оренди в ігровому клубі. На такому прикладі можна показати декілька основних типів зв'язків між сутностями.

У моделі використовуються:

* `1:N` - один користувач може мати декілька бронювань;
* `1:N` - один стіл або зона може мати декілька бронювань у різний час;
* `M:N` - одне бронювання може містити декілька настільних ігор, а одна гра може використовуватись у різних бронюваннях;
* `1:N` - один користувач може залишити декілька відгуків;
* `1:N` - один стіл або зона може мати декілька відгуків.

Зовнішні ключі використовуються для зв'язку між залежними сутностями та їх батьківськими сутностями.

## 2. Нормалізація до 3NF

### 1NF

Всі поля містять одне значення і не містять списків або масивів.

Наприклад, інформація про користувача зберігається в окремих полях `full_name`, `email` та `phone`, а настільні ігри не записуються списком в одному полі.

### 2NF

Неключові атрибути залежать від первинного ключа своєї сутності.

Складених первинних ключів у моделі немає, тому часткових залежностей від частини первинного ключа немає.

### 3NF

У моделі немає транзитивних залежностей між неключовими атрибутами.

Атрибути зберігаються в тій сутності, до якої вони безпосередньо належать.

Наприклад, `hourly_rate` знаходиться в `GameTable`, тому що ціна за годину відноситься саме до конкретного столу або зони.

`total_price` знаходиться в `Booking`, тому що це зафіксована загальна вартість конкретного бронювання на момент його оформлення. Вона не залежить від поточного значення `hourly_rate`, якщо ціна оренди зміниться пізніше.

## 3. Основні виправлення

Під час створення моделі були зроблені такі зміни.

### 1. Зміна типу ID на UUID

Спочатку для різних сутностей були використані різні типи ідентифікаторів. Наприклад, десь був `integer`, а десь `string`.

Це було виправлено. Тепер всі первинні та зовнішні ключі в моделі мають тип `UUID`.

Commit:

`fix(spec): standardize ID types to UUID across all entities`

### 2. Прибрана окрема таблиця для Booking і BoardGame

Спочатку для зв'язку між бронюванням та іграми можна було створити окрему таблицю `booking_games`.

Але цей зв'язок не має власних атрибутів. Тому відповідно до критеріїв прийняття окрему сутність для нього не створювали.

У ER-моделі залишився прямий зв'язок M:N між `Booking` та `BoardGame`.

Commit:

`refactor(spec): remove explicit junction table booking_games`

### 3. Узгодження назв і атрибутів

Було перевірено, щоб назви атрибутів у `spec.md` та Mermaid-діаграмі збігалися.

Зокрема, для загальної вартості бронювання використовується одна назва — `total_price`.

Також для ідентифікаторів та зовнішніх ключів використовується один тип — `UUID`.

Commit:

`fix(spec): align attribute names between spec and diagram`
